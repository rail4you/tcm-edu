# ash-ts-demo

A minimal full-stack skeleton that pairs a **Phoenix 1.8** backend with a
**Next.js** frontend, glued together by **AshTypescript**'s generated RPC
client.

The point of the project is to show one way to ship a Phoenix + Ash
backend with a fully-static Next.js SPA, without giving up a real RPC
endpoint or a real database. There is **no authentication** so we can
keep the focus on the wiring — drop in `:require_authenticated_actor`
policies on `AshTsDemo.Todo` and a `tenant` config when you're ready.

## What's in the box

```
.
├── config/                 # Phoenix + AshTypescript config
├── lib/ash_ts_demo/        # Todo resource + domain (Ash)
├── lib/ash_ts_demo_web/    # Endpoint, router, RPC + SPA controllers
├── priv/
│   ├── repo/migrations/    # auto-generated by ash_postgres
│   └── app/                # Next.js static export target (build artefact)
└── frontend/               # Next.js 16 + Tailwind 4 + TypeScript 5
    └── lib/generated/      # mix ash_typescript.codegen output
```

The generated TypeScript lives at
`frontend/lib/generated/{ash_rpc,ash_types,ash_zod}.ts` and is committed
to the repo so the frontend can type-check without first running
`mix`. Re-run `mix ash_typescript.codegen` whenever you change a
resource or RPC action.

## Prerequisites

| Tool    | Version (tested) | Where used |
|---------|------------------|------------|
| Elixir  | 1.18 / OTP 27    | Phoenix    |
| Node    | ≥ 22             | Next.js    |
| pnpm    | ≥ 10             | Next.js    |
| Postgres | 13+            | AshPostgres |

The default DB config points at `localhost:5433` with `postgres/postgres`
credentials. Override with the standard `PG*` env vars or `DATABASE_URL`
(see `config/{dev,runtime}.exs`).

## First-time setup

```bash
mix setup                                    # get deps + create + migrate DB
mix ash_typescript.codegen                   # write TypeScript client (idempotent)
pnpm --dir frontend install                  # install Next.js deps
```

## Development — two processes

Run the two servers in separate terminals:

```bash
# Terminal 1 — Phoenix (RPC + DB)
mix phx.server                               # http://localhost:4000

# Terminal 2 — Next.js dev server (HMR)
pnpm --dir frontend dev                      # http://localhost:3000
```

Open `http://localhost:3000`. RPC calls hit `/api/rpc/*` on port 3000,
which Next.js transparently rewrites to Phoenix on port 4000 (see
`frontend/next.config.mjs`). CORS is wired up in the `:api` pipeline.

## Production — single process

Build the static frontend into `priv/app/` and let Phoenix serve
everything:

```bash
pnpm --dir frontend build                    # → priv/app/
MIX_ENV=prod mix phx.server                  # http://localhost:4000
```

Visit `http://localhost:4000/app/`. `Plug.Static` (configured in
`AshTsDemoWeb.Endpoint`) serves the static files; `FallbackController`
returns `index.html` for unmatched paths so Next.js client-side routing
works.

## The Todo resource

`lib/ash_ts_demo/todo.ex` declares a Postgres-backed `Ash.Resource` with
`uuid_primary_key :id`, `title` and `completed` attributes, and a
`policy always() -> authorize_if always()` so anyone can hit it.

`lib/ash_ts_demo/todo_domain.ex` enables `AshTypescript.Rpc` and
declares five `rpc_action`s — `list_todos`, `get_todo`, `create_todo`,
`update_todo`, `delete_todo`. These become TypeScript functions with
the same names plus their result/input types in `ash_rpc.ts`.

## Re-generating the RPC client

```bash
mix ash_typescript.codegen                   # write ts files
mix ash_typescript.codegen --check           # fail in CI if out of date
```

Outputs:

- `frontend/lib/generated/ash_rpc.ts`     — fetch functions and result types
- `frontend/lib/generated/ash_types.ts`   — resource schemas, filters, sorts
- `frontend/lib/generated/ash_zod.ts`     — Zod schemas for runtime validation

The endpoint URLs (`/api/rpc/run`, `/api/rpc/validate`) are baked into
`ash_rpc.ts` at codegen time. Change them via
`config :ash_typescript, :run_endpoint` if you re-route.

## Database tips

```bash
mix ecto.migrate                            # apply pending migrations
mix ecto.rollback                           # roll back the last one
mix ash_postgres.generate_migrations \
  --name add_whatever                        # scaffold a new migration
```

Migrations live under `priv/repo/migrations/` and
`priv/resource_snapshots/` (the latter is how AshPostgres knows your
resource shape).

## Verifying the end-to-end flow

```bash
mix compile                                 # 0 warnings
mix ecto.migrate                            # DB up to date
mix ash_typescript.codegen                  # 3 ts files emitted
pnpm --dir frontend tsc --noEmit            # 0 ts errors
pnpm --dir frontend build                   # writes priv/app/

# smoke test
curl -s -X POST http://localhost:4000/api/rpc/run \
  -H 'Content-Type: application/json' \
  -d '{"action":"list_todos","fields":["id","title","completed"]}'
# => {"data":[],"success":true}
```

## Notes & caveats

- **phoenix_live_view is a dependency but no LiveView routes are
  mounted.** It stays in `mix.exs` only to verify that adding LiveView
  later does not break the Next.js routing — feel free to drop it if
  you know you won't use it.
- **`force_ssl` is intentionally disabled in `config/prod.exs`.** That's
  so `MIX_ENV=prod mix phx.server` works over plain HTTP for local
  verification. Re-enable it (and supply `SECRET_KEY_BASE`,
  `DATABASE_URL`, etc.) when you ship somewhere real.
- **`picosat_elixir` is included.** Ash's policy authorizer needs a SAT
  solver — `picosat_elixir` is a fast NIF binding. Swap for
  `simple_sat` if you want a pure-Elixir fallback.
- **The Todo list is wide-open.** Add policies like
  `policy action_type(:create) do authorize_if actor_present?()` once
  you have an `AshAuthentication` setup.
- **`priv/app/` is build output.** It is regenerated on every
  `pnpm build`. `.gitkeep` is the only thing tracked there in git.
